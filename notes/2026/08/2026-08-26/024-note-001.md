# 代码评审的关注顺序：性能与复杂度权衡

**日期**：2026-08-26　**领域**：工程　**编号**：24/5000

## 背景

先量化再优化，凭感觉换实现经常得不偿失。这里围绕「代码评审的关注顺序」做一次整理，重点放在能直接落地的部分。

## 要点

- 先看接口契约与错误路径，再看实现细节
- 评论区分阻塞项与建议项，避免全部标为必须修改
- 优化前后都要有可复现的基准数据。

## 示例

```bash
## 阻塞
- 未处理上传失败，会静默丢数据
## 建议
- 循环内可提前返回
```

## 易错点

- 只挑格式问题会让真正风险被淹没

## 小结

代码评审的关注顺序 在性能与复杂度权衡这一面，结论可以归纳为：把前提写清楚、把失败路径覆盖到，剩下的就是按数据调优。
