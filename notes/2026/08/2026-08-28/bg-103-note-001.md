# 代码评审的关注顺序：方案对比与选型

**日期**：2026-08-28　**领域**：工程　**编号**：103/9000

## 背景

把候选方案的代价列清楚，选型就不再靠偏好。这里围绕「代码评审的关注顺序」做一次整理，重点放在能直接落地的部分。

## 要点

- 先看接口契约与错误路径，再看实现细节
- 评论区分阻塞项与建议项，避免全部标为必须修改
- 选型结论要写清前提，否则换个环境就不成立。

## 示例

```bash
## 阻塞
- 未处理上传失败，会静默丢数据
## 建议
- 循环内可提前返回
```

## 易错点

- 只挑格式问题会让真正风险被淹没

## 小结

代码评审的关注顺序 在方案对比与选型这一面，结论可以归纳为：把前提写清楚、把失败路径覆盖到，剩下的就是按数据调优。
